# Vyuham audit and roadmap

*2026-11-21. Read-only audit: nothing in the product was changed to produce it. Every finding below was checked
in the code or against the running system; where something wasn't measured, it says so.*

## How this was checked

- Repository: `main` at `a72d933` (69 commits). Backend 12,955 lines of Python across 20 routers; frontend
  Next.js 15.5 App Router with 22 app routes and 11 marketing routes.
- Live site: probed `https://vyuham-six.vercel.app` (pages, `/api/*`, `/api/auth/*`) and listed the Vercel
  project's production environment variable **names** (no values were read).
- Data accuracy: fed deliberately messy CSVs through the real `ingest()` and the real DuckDB casting rules.
- Tests: the full backend suite (345 tests), the 6 new "show the work" tests, frontend typecheck and lint.
- Not measured: production bundle size and page speed (a production build can't run while the local `next dev`
  is running; see the `no-build-while-dev-running` note), and API latency under load.

## P0: broken, unsafe or wrong (fix before anything else)

### P0-1. Production can't sign anyone in, and has no backend
**Evidence.** On the live site, `/api/auth/get-session` and `/api/auth/ok` return **HTTP 500**, and every other
`/api/*` path returns Vercel's `DNS_HOSTNAME_RESOLVED_PRIVATE`. The Vercel production environment has exactly one
variable, `BETTER_AUTH_SECRET`. There is no `DATABASE_URL`, so Better Auth falls back to a local SQLite file that
doesn't exist on Vercel (`src/lib/auth.ts`), and no `BACKEND_URL`, so `/api` is proxied to `127.0.0.1:8000`
(`next.config.ts`).
**Impact.** Every "Start free" button on the marketing site leads to a signup that fails. Nobody can use the
product in production today.
**Fix.** This is an infrastructure decision, not a code change (see "Decisions needed" below): a production Postgres
plus a running FastAPI backend, then `DATABASE_URL`, `BACKEND_URL` and the other variables in `DEPLOY.md` set on
Vercel. Until then, the marketing CTAs should point to `/try` (works with no backend) or a waitlist, not `/signup`.

### P0-2. Correcting a column to "number" silently produces wrong totals
**Evidence.** An Amount column containing `₹1,200`, `₹950.50`, `1,050`, `n/a`, `(200)`, `1100` is inferred as
**text** (one non-numeric cell is enough). The product tells users they can correct a column's type; doing so only
changes the label (`PATCH /datasets/{id}`), and the query layer reads the stored text with `TRY_CAST(... AS DOUBLE)`.
DuckDB returns NULL for `'₹1,200'`, `'1,050'`, `'(200)'`, so **the sum shows 1,100 instead of ~3,900–4,100, with
no warning.**
**Fix.** When a column is retyped to number or date, re-run the same normaliser used at upload
(`_normalise_numbers`, date formats) over the stored values, rewrite the Parquet file, and report how many cells
couldn't be read ("3 of 120 values in Amount aren't numbers: n/a, -, Total"). Never cast silently.

### P0-3. Common real-world formats are left unusable
**Evidence** (same test harness):
- One `n/a`, `-` or a "Total" footer row turns a whole number column into text.
- Indian lakh grouping (`₹1,20,000`) isn't recognised as a number.
- `Paid` / `PAID` / `paid` stay separate categories (the FAQ admits this).
- A "Total" row in the date column also stops it becoming a date.
Not silently wrong like P0-2, but the first five minutes on a real export fail, which the board and buyer panel
both flagged as the moment that matters most.
**Fix.** Treat common blanks (`n/a`, `na`, `-`, `—`, `null`, `none`) as empty; accept lakh grouping; detect and
drop trailing total/subtotal rows (with a visible note); offer one-click "merge values that differ only in case".
Show what was fixed after upload.

### P0-4. Docs and branches don't match what's deployed
**Evidence.** `docs/PROJECT-STATUS.md` says production deploys from `main` at `450278b` and that database
connections are "Stashed"; `main` is now at `a72d933` with connections merged, and the last production deploy was
promoted from a `feat/db-connections` preview. The production backend described in `DEPLOY.md` (VPS + Caddy) isn't
reachable from the live site.
**Fix.** After P0-1, update the status doc and make `main` the only production source again.

## P1: onboarding, usability, analytics reliability, dashboards, reporting

| # | Finding | Evidence | Improvement |

| P1-2 | Free-text Ask can't keep the "ask in plain English" promise | Rule-based parser; "no match" on many natural questions | Lead with suggested questions built from the user's columns (`ask.suggestions()` exists); log every no-match question to learn what to support |

| P1-5 | The agency workflow has no template | Templates: Sales, Startup metrics, Expenses | Add a "Monthly client report" template (spend, clicks, conversions, CPC, CPA, ROAS as metrics) on the existing template engine |

| P1-7 | Scheduled email needs a provider | `app/email.py` logs only unless `RESEND_API_KEY` is set | Configure Resend in production, or hide scheduling UI until it can send |
| P1-8 | Frontend has almost no automated tests | 2 unit test files, no end-to-end tests | Add Playwright smoke tests for sign-up → upload → ask → dashboard → PDF |

## P2: automation, modelling, integrations, reusable workflows

- **Reuse next month:** "replace the file" exists (`PUT /datasets/{id}/file`) and keeps charts. Make it the
  headline of the monthly flow ("Upload March's export") and validate that the new file's columns match.
- **Google Sheets sync** (roadmap) to remove the re-upload step.
- **Pipeline history and retries:** syncs and reports run on Celery; surface run history, failures and a retry
  button in one place.
- **Relationships:** SQL Lab already suggests joins (`app/joins.py`); expose saved relationships to the chart
  builder so a non-SQL user can combine two files.
- **Data quality checks:** row-count change and null-rate change alerts per dataset, using the existing alerts engine.

## P3: advanced and later

AI-assisted analytics (must keep "show the work"), orchestration beyond refresh hooks, ecosystem expansion.
Hold these until P0–P1 are done and real users are asking for them.

## Security review

| Topic | Status | Note |
| --- | --- | --- |
| SQL injection | Good | Values bound as parameters; identifiers quoted; SQL Lab is SELECT-only (`validate_select`) inside the sandbox |
| Data isolation | Good | Per-workspace folder for DuckDB, `owned_dataset` checks; worth one cross-tenant test per router |
| File upload | Good | Size and row limits, `defusedxml`, XLSX size check before parsing |
| Credentials | Good | Database passwords encrypted with Fernet/MultiFernet and rotatable keys (`app/crypto.py`), never returned. `CONNECTIONS_KEY` must be set in production (in development a key is derived from `SIGNING_SECRET`) |
| Share links | Good | `secrets.token_urlsafe(24)`, revocable |
| Rate limiting | Present | Middleware with route rules; Redis when `REDIS_URL` is set, otherwise per-process memory (limits don't hold across several workers) |
| CSRF | Relies on cookies | No explicit Origin check on state-changing FastAPI routes; it relies on the session cookie's SameSite setting. Add an Origin/Referer check as defence in depth (low effort) |
| Secrets in git | Clean | Only `.env.example` files are tracked |
| Compliance claims | Keep it that way | The site makes none; don't add SOC 2/ISO language until certified |

## Decisions needed from the founder

1. **Production hosting with no budget.** The backend needs a server with persistent disk for Parquet files, and
   both the app and Better Auth need Postgres. Options: (a) the VPS in `DEPLOY.md` (costs money); (b) free tiers,
   e.g. a free managed Postgres plus a free container host, with the trade-offs of sleeping instances and limited
   disk; (c) until hosting exists, turn the live site's "Start free" into a waitlist and keep `/try` as the demo.
   (c) is free and honest, and could ship today.
2. **First customer.** The board, competitor scan and buyer panel all point away from "small businesses in
   general". Your brief names small digital agencies; the panel surfaced accountants as a channel. Pick one to build
   the template and onboarding for.

## Suggested order of work

1. P0-1 decision, and meanwhile option (c) so the site stops sending people to a broken signup.
2. P0-2: safe retyping (re-normalise, rewrite Parquet, report unreadable cells), with tests.
3. P0-3: blanks, lakh grouping, total rows, case merging, plus a post-upload summary (P1-4).
4. Ship the "show the work" panel (built, tested, not yet committed).
5. P1-5 + P1-6: the agency template and branded PDF/share pages, then validate the 7-step workflow end to end.
6. P1-1, P1-2, P1-8, then P2.

Each step ships as its own small, tested change.
